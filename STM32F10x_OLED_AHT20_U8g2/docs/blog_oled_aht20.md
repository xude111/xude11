# 从点阵到 U8g2：STM32F103 + SSD1306 + AHT20 课程设计复盘

> 本文是《嵌入式系统原理与应用》课程实验的博客版记录，完整代码、Keil 工程和实验报告见文末链接。

## 一、为什么做这个实验

这次实验有两个任务：

- **任务一**：不依赖现成 OLED 库，从零写 SSD1306 驱动，显示学号姓名、AHT20 温湿度，并实现长文本滚动。
- **任务三**：在 CubeMX + HAL 框架下裁剪并移植 U8g2，完成 demo、学号姓名、四向滚动和动画头像。

看起来是两个任务，实际上是一条完整的链路：**I2C 时序 → 显存组织 → 字库 → 图形库 → 页面调度**。把这条链路走通之后，再换屏幕、换传感器，思路都是相通的。

硬件很普通：

| 器件 | 型号 |
|---|---|
| 主控 | STM32F103C8T6 最小系统板（Blue Pill） |
| 显示 | 0.96 英寸 SSD1306，128×64，I2C |
| 传感器 | AHT20 温湿度模块 |
| 调试 | ST-Link V2，USB-TTL |

接线只有两根信号线：PB6 → SCL，PB7 → SDA，OLED 和 AHT20 并联在同一条 I2C1 总线上，地址分别是 0x3C 和 0x38（HAL 写地址 0x78 / 0x70）。

## 二、任务一：自己写一个 OLED 驱动

### 2.1 显存是一张 8 页的“纸”

SSD1306 的 128×64 显存不是按行存储，而是按 **8 个页** 存储，每页 8 行、128 列，每列 1 字节。字节的 bit0 对应页内最上面那行，bit7 对应最下面那行。

所以驱动里只需要一块 1 KB 的数组：

```c
#define OLED_WIDTH       128U
#define OLED_HEIGHT      64U
#define OLED_PAGES       8U
#define OLED_BUF_SIZE    (OLED_WIDTH * OLED_PAGES)

static uint8_t s_gram[OLED_BUF_SIZE];
```

画点时：

```c
s_gram[(y >> 3) * OLED_WIDTH + x] |= (uint8_t)(1U << (y & 7));
```

`y >> 3` 找页，`y & 7` 找页内行。理解这一点之后，画线、画框、画圆都只是在这个函数上做循环。

刷新时先设置页地址和列地址，再连续写 128 字节，一页一页发。这样一次 I2C 传输就能刷一整页，比“一个像素发一次”快太多。

### 2.2 中文字库：让 Keil 不再乱码

一开始我直接在代码里写：

```c
OLED_ShowString(0, 0, "徐正心");
```

结果 Keil 编译出来不是乱码就是缺字。原因是源文件编码、编译器执行字符集和字库编码三者不一致。后来改成 **Unicode 码点数组**：

```c
static const uint16_t TXT_NAME[] =
{
    0x5F90, 0x6B63, 0x5FC3, 0   /* 徐正心 */
};
```

字库用 `FontCN_Get(code)` 按码点查找。这样无论源文件是 GB2312 还是 UTF-8，编译器看到的都是明确的 16 位整数，不会再出问题。

字库本身用 PowerShell + GDI+ 生成：以宋体 16 px 渲染，逐像素取点，每个汉字输出 32 字节（16 行 × 2 字节）。最终只收录界面实际用到的 69 个汉字，缺字会显示一个方框，方便发现。

ASCII 用 Adafruit GFX 的 5×7 字库。为了和 16×16 汉字混排，我把 5×7 字形放在 16 px 行的第 5~11 行，视觉上正好垂直居中。

### 2.3 AHT20：别被 CRC 吓到

AHT20 的流程不复杂：

1. 上电等 40 ms；
2. 读状态，如果 bit3 没置位，发 `0xBE 0x08 0x00` 初始化；
3. 发 `0xAC 0x33 0x00` 触发测量；
4. 等 80 ms；
5. 读 7 字节：状态 + 湿度 20 bit + 温度 20 bit + CRC。

换算公式：

```c
raw_h = ((buf[1] << 16) | (buf[2] << 8) | buf[3]) >> 4;
humidity = raw_h * 100.0f / 1048576.0f;

raw_t = ((buf[3] & 0x0F) << 16) | (buf[4] << 8) | buf[5];
temperature = raw_t * 200.0f / 1048576.0f - 50.0f;
```

CRC8 用多项式 0x31、初值 0xFF。实际调试时发现，个别模块的 CRC 字节和计算值对不上，但温湿度数据是正常的。查资料后确认不同批次的模块可能存在差异，于是改成：**CRC 失败只累计错误计数，不丢数据；只有通信失败或忙标志一直不释放才报错**。这样既保留了校验信息，又不会出现“数据明明能用却一直显示 ERR”的情况。

### 2.4 两种滚动：软件和硬件

长文本 `Hello，欢迎来到重庆交通大学物联网205实训室！` 一共 336 px，屏幕只有 128 px，显然放不下。我用的是软件滚动：每 25 ms 重绘一帧，偏移量按 55 px/s 增长，文本从右向左循环。

核心就一行：

```c
uint32_t pos = (elapsed * 55U) / 1000U;
int16_t x = (int16_t)((int32_t)OLED_WIDTH - (int32_t)pos);
OLED_DrawTextU16(x, 24, TXT_LONG_SCROLL, OLED_TEXT_MIXED16, 1);
```

驱动会自动裁剪超出屏幕的像素，所以不需要手动算可见区间。

SSD1306 还自带硬件滚动：写 `0x26/0x27`（水平右/左）、`0x29/0x2A`（垂直 + 右/左）、`0x2F` 启动、`0x2E` 停止，芯片就会自己移动显存内容，MCU 不用反复重绘。

但硬件滚动有个限制：**它只能滚动当前显存里的内容**，不能把屏幕外的长文本“拉”进来。所以长文本还是得用软件滚动；硬件滚动我用来演示静态图案，页 1~6 参与滚动，页 0 和页 7 固定，标题和底部说明不会跑。

## 三、任务三：裁剪并移植 U8g2

### 3.1 为什么要裁剪

完整 U8g2 很大：几十种显示驱动、几百种字体，还有 mui、u8log 等模块。直接塞进 Keil 工程，编译慢、Flash 占用高，而且大部分代码永远用不到。

我只保留实际用到的 30 个源文件：

- SSD1306 128×64 I2C 全缓冲驱动；
- 5×7、6×10、6×12、7×14B、ncenB10、ncenB14 六种字体；
- 圆、线、框、位图、多边形等图形函数；
- u8x8 的字节通信、CAD、字符串工具。

裁剪原则写在 `Drivers/U8g2/README.md` 里：只留一种屏、一种缓冲模式、demo 用到的字体，其余全部删掉。

### 3.2 移植的关键：字节回调

U8g2 不直接操作寄存器，而是通过 `u8x8` 的字节回调与底层通信。我们要做的就是实现“收到 START → 清空缓冲；收到 SEND → 追加字节；收到 END → 调用 HAL 发送”。

```c
static uint8_t U8g2_ByteCb(u8x8_t *u8x8, uint8_t msg, uint8_t arg_int, void *arg_ptr)
{
    switch (msg)
    {
        case U8X8_MSG_BYTE_START_TRANSFER:
            s_tx_len = 0;
            return 1;
        case U8X8_MSG_BYTE_SEND:
            /* 追加 arg_int 个字节到 s_tx_buf */
            return 1;
        case U8X8_MSG_BYTE_END_TRANSFER:
            HAL_I2C_Master_Transmit(&hi2c1, OLED_I2C_ADDR, s_tx_buf, s_tx_len, 100);
            return 1;
        default:
            return 0;
    }
}
```

初始化：

```c
u8g2_Setup_ssd1306_i2c_128x64_noname_f(&s_u8g2, U8G2_R0,
                                       U8g2_ByteCb, U8g2_GpioDelayCb);
u8g2_InitDisplay(&s_u8g2);
u8g2_SetPowerSave(&s_u8g2, 0);
```

全缓冲模式在 RAM 里维护 1 KB 缓冲区，`u8g2_SendBuffer()` 时整屏发送。这样画面不闪，也充分发挥了硬件 I2C 的连续传输能力。

### 3.3 Demo 页：验证图形和字体

Demo 页放了一个圆、一个转动的指针、一个往复的进度条，以及三种字体。指针用 16 点正弦/余弦表驱动，每 140 ms 走一步；进度条每 80 ms 变一次。

这一页看起来简单，但它同时验证了：图形函数、字体渲染、缓冲区刷新、I2C 回调、时间基准都正常。如果 demo 能稳定运行，后面的页面基本不会有大问题。

### 3.4 四向滚动：负坐标是个坑

四向滚动要求文字从左、右、上、下四个方向进出屏幕，每 3 秒换一个方向。

水平滚动直接改 x 坐标即可：

```c
case 0: x = 128 - 70 * t / 1000;              /* 右 → 左 */
case 1: x = -text_w + 70 * t / 1000;          /* 左 → 右 */
```

垂直滚动把六个汉字竖着排，再整体改 y 坐标：

```c
case 2: top = 64 - 60 * t / 1000;             /* 下 → 上 */
case 3: top = -108 + 60 * t / 1000;           /* 上 → 下 */
```

但 `u8g2_DrawXBMP()` 的坐标参数是无符号类型，传负值会被解释成很大的正数，结果就是花屏。解决办法是自己写一个 `T3_DrawCellClip()`：先判断字符是否完全在视口外；部分可见时复制点阵，按 `skip_x`/`skip_y` 平移，只画可见部分。

另外用 `u8g2_SetClipWindow(&s_u8g2, 0, 11, 128, 55)` 把滚动内容限制在 y=11~54，标题和底部方向标签就不会被盖住。

### 3.5 动画头像：两帧就够了

头像 56×56，两帧：睁眼和眨眼。每 2 秒一个周期，前 1.55 秒睁眼，后 0.45 秒眨眼，刷新间隔 80 ms。

两帧只有眼睛区域不同，生成脚本 `tools/gen_avatar.ps1` 直接构造 XBMP 点阵。温度计和水滴图标也用同一脚本手工画，16×16 下轮廓很清楚。

## 四、那道 I2C 题：虚拟逻辑分析仪里 SDA 到底显示什么

题目问：在 Keil 的虚拟逻辑分析仪中，I2C 的 SDA 会显示什么？

我的理解是：**它显示的是数字电平波形，不是解码后的协议包。**

正常有从机时，一次写操作应该是：

```
空闲高 → START（SCL 高时 SDA 下降）
→ 8 位地址（0x78 = 0111 1000，MSB 在前）
→ 第 9 个时钟 ACK（从机把 SDA 拉低）
→ 8 位数据（例如 0xA5 = 1010 0101）
→ 第 9 个时钟 ACK
→ STOP（SCL 高时 SDA 上升）
```

逻辑分析仪只会画高低电平，不会自动标注“地址 0x78”或“ACK”。要自己按 SCL 的 9 个时钟一组去数。400 kHz 时 SCL 周期是 2.5 μs，100 kHz 时是 10 μs。

如果没有真实从机，最常见的是：START 和地址位都有，但第 9 个时钟 SDA 保持高电平（NACK），HAL 返回 `HAL_ERROR` 或 `HAL_TIMEOUT`，SCL 可能停在那里，SDA 一直高。要是 SDA 被短路到地，可能一直低，甚至总线锁死，需要发 9 个 SCL 脉冲解锁。

所以，**SDA 不会自动显示温度数据**。它只反映 MCU 试图发送的电平；只有从机正确应答，后面的数据才有意义。

如果没法真实抓 I2C，我总结了几种替代方案：

1. **USB 逻辑分析仪 + PulseView/sigrok**：最实用，几十块钱就能自动解码地址、数据、ACK。
2. **示波器 I2C 解码**：能同时看模拟波形质量，适合排查上升沿和干扰。
3. **第二块 MCU 嗅探**：用 Arduino/ESP32 采样总线，通过串口转发。
4. **固件日志**：打印 HAL 返回值、`HAL_I2C_GetState()`、SR1/SR2 寄存器、错误码。
5. **总线扫描**：用 `HAL_I2C_IsDeviceReady()` 遍历 0x08~0x77，快速确认地址。
6. **显示自检**：让 OLED 显示棋盘格、全亮、全灭，验证写路径。
7. **降速/替换法**：从 400 kHz 降到 100 kHz，换短线、换模块，快速排除硬件问题。

我实际排查时，先看 OLED 和 AHT20 是否有 ACK，再看 HAL 返回值，最后才用逻辑分析仪抓波形。顺序很重要：先确认“器件在不在”，再确认“时序对不对”。

## 五、踩过的坑

### 5.1 双 Target 并不能隔离源文件

一开始我想在一个 Keil 工程里建两个 Target，结果 Build 时两个应用文件都被编译，Flash 占用异常。后来改成两个独立的单目标工程，共用驱动和 HAL，通过 `TASK3_BUILD` 宏区分入口，问题解决。

### 5.2 汉字字库不是越多越好

第一版字库塞了很多备用汉字，Flash 占用明显变大。后来只保留界面实际用到的 69 个，缺字显示方框，反而更容易发现遗漏。

### 5.3 硬件滚动不是“万能滚动”

SSD1306 的硬件滚动只能移动显存内容，不能把屏幕外的长文本拉进来。长文本必须软件滚动，硬件滚动适合静态图案和广告牌效果。

### 5.4 AHT20 的 CRC 不一定可靠

不同批次模块的 CRC 实现可能有差异。我的策略是“CRC 失败只计数，不丢数据；通信失败才报错”，实际使用更稳定。

## 八、写在最后

这次实验最大的收获不是“点亮了一块 OLED”，而是理解了从寄存器到图形库的完整分层：

- 最底层是 I2C 的 START/ACK/STOP 和 SSD1306 的命令/数据；
- 中间是显存、页地址、字库和裁剪；
- 上层是页面调度、滚动和动画；
- 再往上才是 U8g2 这样的图形库。

每一层都搞清楚之后，换一块屏、换一个传感器，甚至换一个 MCU，都能很快迁移。这大概就是嵌入式开发最有意思的地方。
